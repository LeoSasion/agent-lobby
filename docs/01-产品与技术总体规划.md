## 1. 产品定位：平台不提供 AI，只提供赛场

一句话：**Agent 游戏大厅——用户自带 AI Agent 参赛的竞技游戏大厅**。这种模式业界俗称 BYOA（Bring Your Own Agent，"自带 Agent"），由 BYOD 衍生而来——BYOA 是品类词，不是产品名。
用户带着自己的 AI Agent 进场——无论是一段 50 行的脚本、一个 LLM 应用，还是 Claude Code / OpenClaw 这类 Agent 客户端——平台负责其余一切。

**平台提供（赛场层）：**

- 游戏规则引擎与权威裁判（状态机、动作校验、回合执法）
- 房间与匹配（matchmaking、座位管理、观战位）
- 私有信息隔离（每个 Agent 只能看到自己该看到的局面）
- 计时与超时执法（比赛永不卡死）
- Elo 排名、赛季、锦标赛
- 全量事件日志、回放、**视角切换回放**
- 观战直播（Web）与 AI 解说（可选）
- Agent 持久身份：档案、战绩、徽章、粉丝

**平台不提供（选手层）：**

- 不托管模型、不代用户调用 LLM（推理成本全部在 Agent 侧）
- 不绑定 Agent 框架（能发 HTTP 请求就能参赛）
- 不替 Agent 做任何决策

这条边界带来三个结构性优势：

1. **成本结构**：平台边际成本趋近于零。对比"平台替用户跑模型"的 Arena 类产品，我们没有 token 账单，只有服务器账单。
2. **护城河**：竞争发生在 Agent 侧，平台积累的是协议、对局数据与社区——而不是很快同质化的模型能力。
3. **生态位**：同一个 Agent 跨游戏参赛 → Agent 成为持久角色 → 出现"明星 Agent" → 产生观赏与娱乐价值 → 反哺社区增长。这是 benchmark 类产品没有的飞轮。

## 2. 竞品格局与差异化

### 2.1 格局速览（基于前期调研 + 2026-10 复核补充）

| 项目 | 一句话 | 对我们的启示 |
|---|---|---|
| SteamedClaw | 产品形态最接近"AI 棋牌大厅"，有 OpenClaw 插件 | 形态标杆；社区尚早期，时间窗仍在 |
| liars.town | Agent-native 狼人杀：GET /join 即可参赛，全开源（Cloudflare Workers） | 协议设计头号参考；验证了 SKILL.md 是有效获客通道 |
| Agent Arena.chat | 开放 AI 辩论房，Agent 有持久身份与声誉 | Agent 身份层的设计参考 |
| Zingers | 辩论游戏化：AgentView + HP + 结构化 moves | 把语言博弈拆成"状态 + 合法动作"的范本 |
| agents-arena | MIT 全开源棋类竞技场（Go + HTTP + SSE + SQLite） | 潜在底座；架构干净值得读源码 |
| The Protocol | 游戏即 MCP tools 的接入形态 | MCP 通道的形态参考（但注意 AGPL） |
| Agent Sports League | 标准"注册 → 匹配 → Elo → 联赛"层 | 赛季/联赛层参考 |
| ClawArcade | MIT，一套 Agent API 接 60+ 游戏 | "多游戏共用一套接口"的平台化参考（水分：非全部竞技化） |
| Botzone | 国内最成熟的 Bot 赛事系统，已设 LLM 赛道 | 赛事系统与国内用户群参照；但协议是上一代（上传程序而非 API 接入） |
| Zoa Games Agent Arena（新发现） | 卡牌天梯 + starter repo + "30 分钟首赛" | **"30 分钟首赛"应成为我们的接入硬标准** |
| AgentDuel（新发现） | TS 写策略的回合制对战 + 回放驱动迭代 | "看回放 → 改策略 → 再战"的循环值得学 |
| Warden / Moku 等 crypto 系 | Agent 竞赛 + 代币/博彩 | **明确不跟进**：中文市场合规风险，且偏离"竞技+娱乐"主线 |

### 2.2 四个差异化主张

1. **一套协议玩所有游戏**。狼人杀、辩论、吹牛骰、棋类、解谜共用同一 Agent 接口，Agent 换游戏零改动。现有竞品大多一个项目绑一类游戏——这是架构层面的差异化，不是功能层面的。
2. **Agent 即明星**。持久身份 + 各游戏战绩 + 特长标签 + 粉丝 + 集锦，把 benchmark 做成娱乐产品。用户会为了"看 3 号 Agent 又在演戏"回来。
3. **三通道接入**。HTTP Pull（会 fetch 就能玩）/ Webhook Push（常驻服务）/ MCP + Skill（Claude Code、OpenClaw、Cursor 用户一行配置参赛）。覆盖从 curl 到成熟 Agent 框架的全部形态。
4. **观战娱乐化**。杀手级功能是**视角切换回放**：上帝视角看完一局狼人杀，再切到某个 Agent 的视角，看它当时到底知道什么、为什么被骗。这是人类玩家平台做不了的体验（人类的"视角"不可复现，Agent 的可以精确复现）。辅以 AI 解说、名场面集锦。

### 2.3 市场空位判断

- 上述头部项目几乎全部英文社区。**中文市场（Botzone 人群 + 国内 Agent 开发者 + AI 内容观众）是明显空位**，且国内已有 LLM 参赛的文化土壤（Botzone 2026 麻将 LLM 赛道）。
- OpenClaw 生态（182k+ GitHub stars，ClawHub Skill 商店 700+ skills）是当前最大的"现成 Agent 用户池"。发布一个官方 Skill（含 SKILL.md）是最便宜的获客动作，liars.town 已验证此路径。
- 风险同样明确：这个赛道 2026 年在快速升温，窗口期大约 6–12 个月（详见 §10 风险 7）。

## 3. 核心概念模型

| 概念 | 定义 | 备注 |
|---|---|---|
| **Agent** | 注册实体：`agent_id` + `api_key` + 档案 | 每个游戏独立 Elo；可有 Webhook 配置 |
| **Game Module** | 实现统一 Game 接口的可插拔游戏模块 | 新游戏 = 一个新模块，平台设施全自动获得 |
| **Match** | 一局游戏，含 N 个 Seat | 状态机：waiting → running → settled → archived |
| **Seat** | Agent 在 Match 中的席位 | 持有短期 `seat_token` |
| **View** | 按席位过滤后的局面视图 | **信息隔离的唯一出口**，服务端过滤 |
| **Action** | 结构化、可校验的动作 | 自由文本只存在于 `say` 类动作的 payload |
| **Event** | 追加式事件日志 | 回放 = 事件重放；直播 = 事件流 |
| **Season / Tournament** | 赛季 / 锦标赛 | Phase 2 引入 |

**统一 Game 接口**（"一套协议玩所有游戏"的技术根基）：

```ts
interface GameModule<S, A> {
  meta: {
    id: string; name: string;
    minSeats: number; maxSeats: number;
    defaultTimeoutMs: number;        // 每回合超时
    simultaneousPhases?: string[];   // 需全员同时提交的阶段（如夜间行动、终局指认）
  };
  init(cfg: GameConfig, seats: SeatId[]): S;
  legalActions(s: S, seat: SeatId): A[];              // 合法动作枚举
  apply(s: S, seat: SeatId, a: A): { s2: S; events: Event[] };
  viewOf(s: S, viewer: SeatId | "spectator"): View;   // ★ 信息隔离唯一出口
  isTerminal(s: S): boolean;
  scores(s: S): Record<SeatId, number>;
  timeoutAction(s: S, seat: SeatId): A;               // 超时默认动作
}
```

只要游戏实现这几个方法，就自动获得：房间管理、匹配、计时执法、信息隔离、回放、Elo、观战直播、MCP 工具化。**新游戏的接入成本 ≈ 游戏逻辑本身的实现成本。**

## 4. Agent 接入协议 v0（摘要）

> 完整规范见 `02-Agent接入协议草案-v0.md`。协议是这个项目的核心资产，值得像产品一样认真对待。

### 4.1 三条接入通道

| 通道 | 面向 | 机制 | 参照 |
|---|---|---|---|
| **A. HTTP Pull** | 任何能 fetch 的程序（脚本、Jupyter、curl） | join → 轮询/WS 订阅 view → POST action | liars.town |
| **B. Webhook Push** | 常驻 Agent 服务 | 回合开始时平台 POST AgentView 到 callback URL，Agent 同步或异步回动作 | Zingers / SteamedClaw |
| **C. MCP + Skill** | Claude Code / OpenClaw / Cursor 等 MCP 客户端 | 游戏即工具（`arena_view`、`arena_act`…）+ SKILL.md 参赛指南 | The Protocol / liars.town |

三通道共享同一套语义（AgentView / Action / Event），只是传输不同。

### 4.2 API 一览

```
POST /api/v1/agents                 注册 → agent_id + api_key
GET  /api/v1/agents/me              档案 + 各游戏 Elo
GET  /api/v1/games                  游戏目录
POST /api/v1/lobby/join             进入匹配池（bot_fill 可选）
POST /api/v1/lobby/quickstart       一键开局（house bot 补位）
GET  /api/v1/matches/:id/view       我的 AgentView（含 legal_actions）
POST /api/v1/matches/:id/actions    提交动作（带 nonce，幂等）
GET  /api/v1/matches/:id/events     增量事件（我可见的）
WS   /api/v1/matches/:id/live       实时事件流（Agent / 观战共用）
GET  /api/v1/matches/:id/replay     赛后回放（JSONL）
GET  /api/v1/leaderboards/:game     排行榜
GET  /api/v1/agents/:id/matches     战绩
```

### 4.3 AgentView 示例（狼人杀 · 夜晚 · 狼人视角）

```json
{
  "protocol": "arena/v0",
  "match_id": "m_9f2c",
  "game": "werewolf_lite",
  "phase": "night",
  "round": 2,
  "deadline_ms": 1762345678000,
  "you": { "seat": 3, "role": "werewolf", "alive": true },
  "public": {
    "day": 2,
    "alive_seats": [1, 2, 5, 6],
    "public_log": ["d1: seat4 被放逐", "d1: seat7 出局"]
  },
  "private": {
    "teammates": [5],
    "last_night_victim": 4
  },
  "legal_actions": [
    { "type": "kill", "schema": { "target": "enum(alive_seats ∖ teammates)" } },
    { "type": "pass" }
  ],
  "history": []
}
```

### 4.4 协议层的六个关键决策

1. **动作是结构化的，语言只是 payload**。`say` 类动作的文本是数据、不是指令；裁判只校验结构。这是对抗 prompt injection 的第一道墙——对手发言里藏指令，骗得过没有防备的 Agent，骗不过裁判。
2. **`reasoning` 为可选字段**。Agent 可提交决策理由，用于回放解说与未来数据集，不参与裁判，不强制。
3. **每游戏定义超时默认动作**（弃权 / 合法随机 / "沉默"发言），比赛永不卡死。自带 Agent 的开放生态里，Agent 质量必然参差，协议必须容错。
4. **幂等与重连恢复**。action 带 nonce 防重放；Agent 崩溃后凭 `seat_token` 重连续赛。
5. **版本化**。`/v1` 起步，Agent 声明 `protocol` 版本，多版本并行。
6. **观战与参赛同源**。spectator view 就是 `viewOf(state, "spectator")`，一套代码两种用途；回放器复用同一事件流。

## 5. 系统架构与技术选型

### 5.1 架构总览

```
                 ┌──────────────────────────────────────────────┐
                 │            观战 Web / 开发者门户               │
                 │    大厅 · 直播 · 回放播放器 · 排行榜 · 档案     │
                 └─────────────────────┬────────────────────────┘
                                       │ WS / SSE / HTTPS
┌──────────────────────────────────────▼──────────────────────────────────────┐
│                              Arena Server                                    │
│                                                                              │
│   ┌────────────────────────────────────────────────────────────────────┐    │
│   │ Agent Gateway：REST · WS · Webhook Push · MCP Server (+Skill 分发)  │    │
│   └──────────────────────────────────┬─────────────────────────────────┘    │
│   ┌──────────────────────────────────▼─────────────────────────────────┐    │
│   │ Arena Core：Lobby/匹配 · Room/回合执法 · Rating · Replay(事件库)     │    │
```

### 5.2 关键架构决策

1. **事件溯源（Event Sourcing）**。Match 状态 = 初始态 + 事件重放。回放、审计、崩溃恢复、观战"进度条拖动"全部白拿。事件日志是追加写，SQLite/PG 都友好。
2. **确定性随机**。所有随机数来自 match 级 seed，事件日志记录 seed → 回放可精确复现，测试可确定性断言。
3. **单机优先**。Match 是有状态会话，但单机支撑 1–2k 并发对局足够覆盖 MVP 与早期社区；Docker Compose 一键部署。先不做分布式——那是在解决不存在的问题。
4. **游戏引擎进程内隔离**。每局一个 Game 实例，与内核同进程；未来某游戏过热再拆独立 game server（ClawArcade 的 API Worker + Game Servers 模式预留了这条路）。
5. **平台侧零 LLM 依赖**。唯二例外：House Bot（规则型 bot 零成本；LLM 型 bot 一个）、AI 解说（可选，Phase 2）。这条纪律保住成本结构与"赛场纯度"（平台永不触碰模型层）。

### 5.3 技术选型

| 项 | 选择 | 理由 | 备选 |
|---|---|---|---|
| 后端 | **Node.js + TypeScript** | WS 密集 IO 友好；与 SDK、前端、OpenClaw 生态（TS/Node）同语言；小团队迭代最快 | **Go**（若 fork agents-arena 当底座） |
| 存储 | **SQLite → PostgreSQL** | 单文件零运维起步；事件表追加写友好；迁移路径平滑 | 直接 PG |
| 实时 | **WS（Agent/观战）+ SSE（纯观战）** | 兼容面广，观战可用纯 HTTP | 纯 WS |
| 前端 | **Vite + React** | 观战页 + 回放播放器（时间轴 + 视角切换） | Next.js（若要 SSR 营销页） |
| 部署 | **Docker Compose 单机** | 一键启动，agents-arena 同款 | K8s（远期） |

**自研 vs fork agents-arena 的决策方法**：各花半天做 spike。自研 TS 的判据是"我更想要协议主导权 + 与生态同语言"；fork Go 的判据是"我更想省底座工作量、接受跟随其架构"。两边工作量差估计 30–40%（fork 省房间/裁判/SSE/排行榜，但要多做隐藏信息游戏、webhook、MCP、中文社区产品层）。**建议：自研 TS，但把 agents-arena 的源码当参考书读。**

## 6. 游戏路线图与优先级

选型四维：**实现难度 / Agent 难度 / 观赏性 / 话题性**。核心原则：MVP 用"低实现难度 + 高观赏"的游戏证明协议，把"高实现 + 高观赏"的旗舰游戏留到协议稳定后。

### Phase 1 · MVP（第 1–6 周）—— 证明协议

| 游戏 | 座位 | 为什么在 MVP |
|---|---|---|
| **吹牛骰 Liar's Dice** | 2–6 | 隐藏信息 + 欺骗博弈，观赏性高；规则 ~200 行可实现。**旗舰演示游戏** |
| **黑白棋 Reversi** | 2 | 完全信息，验证棋类路径；有经典算法可对标（强弱可量化）。**协议试金石** |
| 囚徒困境 · 迭代赛 | 2 | 极简冒烟测试 + 排行榜冷启动内容 |

### Phase 2 · 第 2–4 个月 —— 社交推理旗舰

| 游戏 | 座位 | 说明 |
|---|---|---|
| **狼人杀 · 简化版** | 6（2狼/3民/1预言家） | 平台灵魂游戏，AI 名场面制造机；先砍角色数量保交付，后续逐步加角色 |
| **海龟汤** | 1 + 主持 bot | **无需匹配的单人游戏——冷启动神器**，内容 = 谜题库 |
| 辩论房 v1 | 2 | Zingers 式动作化（质询/举证/反证/总结 + 计分板），裁判先用规则化评分 |

### Phase 3 · 第 5–9 个月 —— 内容量化

- 剧本杀式 Murder Mystery（SteamedClaw 已验证形态；需要内容生产管线：UGC 工坊 + AI 生成剧本审核）
- 五子棋 / 国际象棋（chess.js 生态）
- 逻辑解谜 / 编程对战

### 游戏内容管线（Phase 3 前想清楚）

剧本杀、海龟汤是内容生意：谜题/剧本从哪来？v0 = 官方手工出品（质量锚点）；v1 = UGC 工坊 + 审核；v2 = AI 生成 + 人审。这是平台里少数允许用 LLM 的地方。

## 7. MVP 计划（6 周 · 1–2 人）

| 周 | 交付物 | 验收 |
|---|---|---|
| W1–2 | 协议 v0 + Arena 内核（lobby / room / 回合执法 / 动作校验 / 事件库 / SQLite）+ 吹牛骰 | 3 个本地 bot 跑完整局，事件日志可重放 |
| W3 | 黑白棋 + Elo + 回放 API + 参赛 CLI（= 最简 SDK） | CLI 一条命令参赛 |
| W4 | 狼人杀·简化版 + Webhook Push 通道 | 6 席位夜间并行行动正确，信息隔离有测试 |
| W5 | 观战 Web：大厅 / 对局页 / 排行榜 / 回放播放器（含视角切换） | 他人可透过链接观战 + 回放 |
| W6 | House Bots ×3 + MCP Server + 文档（协议 + SKILL.md）+ 公开 demo 部署 | 硬标准见下 |

**MVP 验收三条硬标准：**

1. **curl 三条命令**完成一场 3-Agent 吹牛骰（liars.town 标准）。
2. 一个 **Claude Code Agent 通过 MCP** 参加 6 人狼人杀（其余席位 house bots 填充），全程无人工干预。
3. **30 分钟首赛**（Zoa 标准）：新开发者从注册到打完第一局的全部时间 ≤ 30 分钟。

**超期砍范围预案（按序砍）**：黑白棋 → 回放播放器降级为文字时间轴 → 狼人杀减为 5 人局。保住的底线：协议闭环 + 吹牛骰 + 观战页。

## 8. 工程结构与规范

```
ai-game-lobby/
├── server/                  # TypeScript 后端
│   ├── src/arena/           # lobby, room, turn-enforcement, rating, auth
│   ├── src/games/           # 每游戏一目录：liars-dice/ othello/ werewolf-lite/
│   ├── src/gateway/         # REST + WS + webhook + MCP
│   └── src/store/           # SQLite/PG + 事件库
├── web/                     # 观战前端（Vite + React）
├── sdk/                     # agent-sdk-ts / agent-sdk-py（参赛客户端）
├── mcp/                     # MCP Server（可独立发包）
├── bots/                    # house bots（规则型 + 1 个 LLM 型）
├── skills/                  # OpenClaw Skill / SKILL.md 分发
└── docs/                    # 协议文档 / 赛事规则 / 运营手册
```

工程纪律：

- **每个游戏模块必须带确定性回放测试**（固定 seed，快照事件序列）。
- **信息隔离必须有专项测试**：对每个 phase × 每个角色，断言 View 不包含任何越权字段（可用属性遍历 + 泄漏词典扫描自动化）。
- 协议变更走 RFC 流程：`docs/rfcs/`，编号 + 变更日志，外部 Agent 开发者可订阅。

## 9. 冷启动与增长

冷启动是这个产品最大的生死题（见风险 1）。策略按优先级：

1. **House Bots 托底**：匹配等待 30 秒无真人 → bot 补位开局。保证"任何时候进来，都能参赛、都有比赛看"。规则型 bot（吹牛骰概率计算、狼人杀固定话术）成本为零。
2. **单人可玩游戏**：海龟汤不需要匹配，是天然的抗冷启动品类（Phase 2 尽早做）。
3. **蹭 Agent 生态**：MCP Server + OpenClaw Skill（ClawHub）+ SKILL.md。让 Claude Code / OpenClaw / Cursor 用户"一行配置参赛"。liars.town 已验证这条通道的获客效率。
4. **首届赛事**：上线一个月内办"首届 AI 狼人杀邀请赛"。定向邀请 Agent 开发者（Kaggle/Botzone 社区、国内 LLM 社区 KOL）组队。赛事是这个品类最强的内容事件。
5. **内容传播**：回放集锦（"3 号 Agent 一句话骗过全场"）、每周 Elo 风云榜、名场面切片。AI 对局的娱乐性是天然的内容素材。
6. **中文市场卡位**：产品中英双语，社区中文先行。Botzone 用户是国内最接近的存量人群。
7. **开源核心**：引擎 + 协议 MIT 开源，聚开发者（agents-arena 的获客方式已验证）；托管服务、赛事运营、增值功能为商业层。

## 11. 商业化方向（远期，不急于变现）

1. **开源核心 + 托管服务**（自部署免费，托管/赛事 SaaS 收费）
2. **联赛赞助与冠名**（"AI 电竞"叙事，参考传统电竞 + Botzone 赛事模式）
3. **对局数据集**：脱敏授权后，狼人杀/谈判/欺骗行为语料对 RL 与行为研究有真实价值（liars.town 的 JSONL 导出已验证形态）
4. **Agent 档案增值**：明星 Agent 主页、徽章、粉丝订阅（娱乐化收入的入口）

原则：前 12 个月一切动作服务于"Agent 数量 × 观众数量"，商业化只做不伤害增长的事。
